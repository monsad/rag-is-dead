TL;DR

Cztery tezy tej prezentacji

🤖

1 · Autouzupełnianie to już nie jest produkt

Wartość przeniosła się z „podpowiedz linijkę" na „wykonaj zadanie i otwórz PR". Copilot, Claude Code i Codex konkurują teraz na poziomie harnessu agenta, nie modelu.

🔐

2 · Agent w CI to nowa powierzchnia ataku

Agent czytający untrusted input (issue, komentarz, diff z forka) z uprawnieniami pipeline'u = prompt injection z dostępem do sekretów. To już nie teoria — 2026 przyniósł działające exploity.

☸️

3 · Kubernetes dojrzał do inferencji

DRA GA (1.34), Gateway API Inference Extension, vLLM/llm-d. Self-hosting przestał być projektem badawczym — stał się decyzją kosztową i compliance'ową.

🧭

4 · Nie ma „najlepszego modelu"

Jest najlepszy model dla danej ścieżki. Routing per zadanie (koszt × jakość × latencja) bije wybór jednego dostawcy na wszystko.

Jeden brand, sześć różnych produktów

Praktyka

Agent jest tak dobry, jak jego kontekst

📄 AGENTS.md / custom instructions

Konwencje repo, sposób uruchamiania testów, czego nie ruszać, definicja „done". To najtańsza inwestycja o największym zwrocie — jeden plik zmienia jakość każdego uruchomienia.

🎭 Custom agents

Wyspecjalizowani agenci z własnym promptem i zawężonym zestawem narzędzi: migrator testów, reviewer bezpieczeństwa, bumper zależności. Wąski zakres = przewidywalny wynik.

🔌 MCP — narzędzia i dane

Model Context Protocol podpina agentowi issue trackera, dokumentację, bazę, monitoring. Zasada: minimalny zestaw narzędzi — każde kolejne to i ryzyko, i gorsze decyzje modelu.

🧪 Zielony pipeline jako feedback

Agent bez szybkich testów i lintera zgaduje. Z nimi — iteruje. Czas test+lint to realny parametr jakości agenta, nie tylko DX.

Reguła kciuka: jeśli nowy człowiek w zespole nie zrobiłby zadania z samego README — agent też nie zrobi. Napraw dokumentację, zanim obwinisz model.

Realizm

Do czego agent nadaje się dziś, a do czego nie

Wysoka skuteczność
  • Testy do istniejącego kodu i uzupełnianie pokrycia
  • Mechaniczne migracje (API, framework, składnia) w wielu plikach
  • Bugi z reprodukcją: stacktrace + failing test
  • Boilerplate: endpointy, DTO, klienci, konfiguracja
  • Pierwsza warstwa review: literówki, null-safety, brak testu
  • Dokumentacja i changelogi z diffa
Niska skuteczność / wysokie ryzyko
  • Decyzje architektoniczne i trade-offy międzyzespołowe
  • Zmiany w kodzie bez testów i bez właściciela
  • Wydajność i współbieżność — wymagają pomiaru, nie intuicji
  • Domenowe reguły biznesowe nieopisane nigdzie w repo
  • Zadania „posprzątaj repo" bez zdefiniowanego zakresu
  • Cokolwiek, czego nikt nie zweryfikuje przed merge

Anti-pattern numer jeden: PR-y wygenerowane szybciej, niż zespół jest w stanie je zrecenzować. Przepustowość review staje się nowym wąskim gardłem — planuj ją świadomie.

CI/CD

Gdzie realnie wpiąć LLM w pipeline

Pre-commit / lokalnieKonwencja commitów, szybki self-review diffa, generowanie testów przed pushem. Najtańsze i bez sekretów.
Na PR (najlepszy ROI)Automatyczne review, opis PR z diffa, wykrywanie brakujących testów, sprawdzenie zgodności z konwencjami repo.
Po nieudanym buildzieTriage logów: co pękło, czy to flake, czy regresja — z propozycją patcha zamiast surowego stacktrace'a.
Zadania zaplanowaneNocne bumpy zależności, migracje, porządki w TODO, aktualizacja dokumentacji. Wynik zawsze jako PR do review.
Release i produkcjaRelease notes z commitów — OK. Automatyczny merge lub deploy sterowany przez agenta — nie. Gate zostaje przy człowieku.

Zasada: agent proponuje, pipeline weryfikuje, człowiek zatwierdza. Każdy krok, w którym agent jest jedyną kontrolą, jest krokiem za daleko.

Co zyskujesz

Automatyzacja opisana językiem naturalnym zamiast setek linii YAML-a i skryptów, które i tak nikt nie utrzymuje.

Co tracisz

Determinizm. Ten sam trigger może dać inny wynik — więc każdy efekt musi przechodzić przez ten sam gate co kod człowieka.

Warunek wejścia

Uprawnienia tokenu ograniczone do minimum, brak sekretów w zasięgu agenta, wszystko z untrusted źródeł traktowane jako dane.

Bezpieczeństwo · 1/2

Prompt injection w CI to realny incydent, nie teoria

Wejście

Untrusted input

Treść issue, komentarza, opisu PR, nazwa brancha, diff z forka. Każdy z darmowym kontem GitHuba może je wstrzyknąć.

Przywilej

Uprawnienia pipeline'u

Agent działa jako zaufany aktor CI: tokeny, klucze do rejestru, dostęp do zapisu. Model nie odróżnia „danych" od „polecenia".

Wyjście

Kanał eksfiltracji

Komentarz, commit, request sieciowy. Sekret wyprowadzony do publicznego wątku wygląda jak normalna aktywność bota.

Te trzy elementy razem to cała podatność — nie trzeba żadnego błędu w kodzie. W 2026 badacze (m.in. CSA, Aikido, Microsoft Security) pokazali działające ataki tej klasy przeciw akcjom AI od wielu dostawców naraz.

Wcześniej atakujący potrzebował write access. Teraz wystarczy, że założy issue.

Bezpieczeństwo · 2/2

Checklista hardeningu agentów w CI

Zrób to dziś
  • Pinuj akcje do pełnego SHA, nie do tagu
  • Wytnij lub ściśle ogranicz pull_request_target z checkoutem forka
  • permissions: jawnie, domyślnie read, zapis punktowo
  • Sekrety tylko w jobach, do których agent nie ma dostępu
  • Allowlist sieci wychodzącej dla runnera agenta
  • Wymagany human approval przed merge — bez wyjątków
Czerwone flagi w review workflow
  • Treść issue/komentarza wklejana wprost do promptu jako instrukcja
  • Agent z contents: write na triggerze od osoby z zewnątrz
  • GITHUB_TOKEN lub klucze API w tym samym środowisku co agent
  • Brak limitu iteracji i budżetu — agent w nieskończonej pętli
  • Logi agenta bez retencji i bez audytu, kto co uruchomił
  • Automerge po zielonym CI, bez oczu człowieka

Model mentalny: traktuj agenta w CI jak zewnętrznego kontrahenta z dostępem do repo — najmniejsze możliwe uprawnienia, wszystko logowane, nic nie wchodzi na main bez podpisu człowieka.

Kubernetes · 2/5

Stos do serwowania modeli (2026)

Klient / aplikacjaZwykle API zgodne z OpenAI — dzięki temu przełączanie między własnym modelem a dostawcą to zmiana base_url.
Inference GatewayGateway API Inference Extension (SIG-owy standard K8s): routing świadomy modeli, kolejek i KV-cache — zamiast round-robina, który zabija cache.
Silnik inferencjivLLM jako domyślny wybór: continuous batching, PagedAttention, prefix caching. Alternatywy: TensorRT-LLM, SGLang, TGI.
Orkiestracja serwowaniallm-d — rozdzielenie faz prefill i decode na osobne pody; KServe / KubeRay dla klasycznego ML i zadań rozproszonych.
Warstwa GPUSterowniki DRA, MIG lub time-slicing, topologia NVLink. To tu powstaje 80% problemów z wykorzystaniem sprzętu.
ObserwowalnośćMetryki inferencji, nie tylko CPU: TTFT, TPOT, długość kolejki, zajętość KV-cache, tokeny/s per pod.
Kubernetes · 3/5

GPU: od limits: nvidia.com/gpu: 1 do DRA

Stary model — device plugin

Prosisz o liczbę kart. Brak wiedzy o typie, pamięci i topologii. Efekt: model mieszczący się w 20 GB dostaje kartę 80 GB, a inny pod czeka w kolejce.

DRA — GA w Kubernetes 1.34

Deklarujesz właściwości urządzenia (typ, pamięć, interconnect), scheduler dobiera zasób. Sterownik DRA od NVIDII trafił do CNCF — to standard, nie eksperyment.

Kueue — kolejki i kwoty

Admission control ponad schedulerem: kwoty per zespół, priorytety, wywłaszczanie. Konieczne, gdy o te same GPU walczą trening, batch i inferencja.

KAI Scheduler / gang scheduling

Dla klastrów AI: bin-packing, gang scheduling (wszystko albo nic), świadomość topologii. Bez tego zadania wielo-GPU deadlockują się nawzajem.

Dźwignie wykorzystania sprzętu, zanim dokupisz kolejne karty: MIG (twardy podział karty), time-slicing (dla dev/test), kwantyzacja, współdzielenie modelu przez wiele aplikacji.

Kubernetes · 4/5

Autoskalowanie: dlaczego HPA po CPU nie zadziała

Co zawodzi
  • CPU jako sygnał — GPU jest wysycone, CPU śpi
  • Skalowanie po RPS — request to 50 albo 50 000 tokenów
  • Cold start: minuty na pobranie i załadowanie wag
  • Agresywny scale-down — kasuje ciepły KV-cache
Co działa
  • Skalowanie po długości kolejki i zajętości KV-cache (KEDA)
  • SLO na TTFT (pierwszy token) i TPOT (kolejne tokeny)
  • Ciepła rezerwa podów + preloading wag w obrazie lub na wolumenie
  • Routing sticky per sesja — trafia w gorący prefix cache
  • Osobne pule: interaktywne (niska latencja) vs batch (przepustowość)

Inferencja LLM to workload stanowy w praktyce: KV-cache czyni z „bezstanowego" poda coś, co ma pamięć i historię. Traktowanie go jak zwykłego kontenera HTTP to najczęstsza przyczyna złych ogonów latencji i przepalonego budżetu GPU.

Podsumowanie

Sześć rzeczy do zabrania ze sobą

01
Kontekst bije model. AGENTS.md, szybkie testy i czyste konwencje dają większy skok jakości niż zmiana dostawcy.
02
Agent proponuje, człowiek zatwierdza. Automatyczny merge lub deploy sterowany przez model to ryzyko bez pokrycia w korzyści.
03
Prompt injection w CI jest realny. Minimalne uprawnienia, brak sekretów przy agencie, akcje pinowane do SHA — to higiena bazowa, nie hardening dla paranoików.
04
Review jest nowym wąskim gardłem. Skoro generowanie kodu przestało być kosztowne, planuj przepustowość weryfikacji.
05
K8s do inferencji dojrzał — ale nie dla każdego. DRA, vLLM i Inference Gateway są gotowe; uzasadnia je compliance albo stały wolumen, nie sama chęć oszczędzania.
06
Mierz koszt ukończonego zadania. Nie tokeny, nie linie kodu, nie acceptance rate — DORA plus rework plus rachunek za modele.
